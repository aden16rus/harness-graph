# Roadmap разработки Harness Agent (PHP Core + Go Daemon + Svelte 5)

Документ содержит пошаговый план разработки модульного автономного harness-агента с мультиагентной иерархией, выполнением команд в Docker-контейнерах проекта и интерактивной визуализацией графа вызовов в реальном времени.

---

## Архитектурный обзор системы

```
+--------------------------------------------------------------------------+
|                        Frontend (Svelte 5 SPA)                           |
|  - Svelte Flow (@xyflow/svelte): динамический граф нод и связей          |
|  - Inspector Panel: диалог агента, логи вызова тулов, Human-in-the-loop  |
|  - Metrics Header: счетчики токенов, latency, время сессии               |
+------------------------------------+-------------------------------------+
                                     | WebSocket (JSON-RPC Events)
                                     v
+------------------------------------+-------------------------------------+
|                     Go Daemon (High-Perf Engine)                         |
|  - WebSocket Hub: трансляция состояния графа и стриминг токенов          |
|  - LLM Client Proxy: OpenAI SSE streaming, замер TTFT/latency/токенов     |
|  - Docker Socket Engine: прямое управление /var/run/docker.sock          |
|  - Local Process Runner: запуск команд в рабочей директории              |
|  - NDJSON Logger: асинхронная запись сырых трейсов на диск               |
+------------------------------------+-------------------------------------+
                                     ^ Unix Domain Socket (/var/run/harness.sock)
                                     | JSON-RPC 2.0
+------------------------------------+-------------------------------------+
|                  PHP 8.3 Core (Domain & Strategy)                        |
|  - ReAct Loop: цикл рассуждений, вызова инструментов и валидации         |
|  - Sub-Agent Tree: контекстная изоляция дочерних сессий                  |
|  - Plugin System: строго типизированные скилы (JSON Schema)              |
|  - Security & Permissions: матрица доступа саб-агентов к скилам          |
|  - SQLite Storage: проекты, команды, промпты, история запусков           |
+--------------------------------------------------------------------------+

```

## Этап 1: Инфраструктурный каркас и Docker Environment

**Цель:** Подготовить изолированную рабочую среду контейнера, обеспечить корректный доступ к сокету Docker хоста и настроить IPC-канал между Go и PHP.

* [ ] **1.1. Базовый Dockerfile и окружение**
* Multi-stage Dockerfile:
* Stage 1 (`builder-go`): сборка легковесного бинарника Go Engine.
* Stage 2 (`builder-frontend`): сборка SPA-бандла Svelte 5 (Vite/Node).
* Stage 3 (`runtime`): образ на базе Alpine/Debian с PHP 8.3 CLI, расширениями `pdo_sqlite`, `pcntl`, `posix`, установленным бинарником Go и статикой фронтенда.




* [ ] **1.2. Конфигурация `docker-compose.yml**`
* Монтирование тома хостового Docker-сокета: `/var/run/docker.sock:/var/run/docker.sock`.
* Монтирование рабочего каталога целевого проекта в `/workspace`.
* Монтирование базы данных и логов: `./data:/data`.
* Настройка прав пользователя (согласование UID/GID для исключения проблем с правами на файлы в `/workspace`).


* [ ] **1.3. IPC-транспорт (Unix Domain Socket)**
* Создание Go-сервера, слушающего сокет `/var/run/harness.sock`.
* Реализация PHP-клиента для синхронных и потоковых запросов к Go по протоколу JSON-RPC 2.0.
* Интеграционный тест: отправка тестового ping-запроса из PHP в Go и получение pong-ответа.

## Этап 2: Go Daemon — Docker Engine, Runner и LLM Proxy

**Цель:** Создать высокопроизводительный слой для асинхронных операций I/O, прямого взаимодействия с Docker API и проксирования запросов к нейросетям.

* [ ] **2.1. Клиент Docker Socket на Go**
* Подключение официального SDK `[github.com/docker/docker/client](https://github.com/docker/docker/client)`.
* Метод `ExecInContainer`:
* Поиск целевого контейнера по имени/ID.
* Инициализация `ContainerExecCreate` с заданным `WorkingDir` и флагами захвата потоков `AttachStdout`/`AttachStderr`.
* Выполнение команды через `ContainerExecStart` с разделением потоков через `stdcopy.StdCopy`.
* Возврат структурированного результата: `exit_code`, `stdout`, `stderr`, `duration_ms`.




* [ ] **2.2. Локальный Runner команд**
* Метод `ExecLocal`: выполнение вспомогательных команд внутри контейнера агента в директории `/workspace` с поддержкой ограничения времени исполнения (`context.WithTimeout`).


* [ ] **2.3. LLM Gateway и Streaming Proxy**
* HTTP/SSE клиент, поддерживающий OpenAI-совместимый формат API (OpenAI, DeepSeek, Ollama, LM Studio, vLLM).
* Параллельная обработка входящего SSE-потока:
* Трансляция текстовых чанков в PHP-воркер.
* Прямая трансляция чанков в WebSocket-хаб интерфейса.


* Парсинг метаданных usage (prompt/completion tokens) и расчет задержек (Time To First Token, суммарный latency).


* [ ] **2.4. Подсистема асинхронного логирования (NDJSON)**
* Неблокирующая запись всех сырых событий, сообщений и tool calls в файлы `/data/logs/{session_id}/{node_id}.ndjson`.

## Этап 3: PHP Core — Доменная модель, БД и ООП-контракты

**Цель:** Спроектировать чистое ООП-ядро без процедурных простыней кода, реализовать репозитории SQLite и строго типизированные интерфейсы подсистем.

* [ ] **3.1. База данных SQLite и схема миграций**
* Создание таблиц:
* `projects`: параметры целевого проекта, пути, соглашения, дефолтный docker-контейнер.
* `teams`: метаданные команды саб-агентов, ссылка на Lead-агента.
* `agents`: идентификаторы, имена, системные промпты, модели, лимиты токенов.
* `agent_skills`: связь агентов и разрешенных скилов (матрица доступа).
* `sessions`: сессии запусков задач с общими агрегированными счетчиками.
* `execution_nodes`: записи об узлах вызовов саб-агентов (иерархия parent/child, статусы, метрики).




* [ ] **3.2. Доменные сущности (Clean Architecture / Domain Layer)**
* Readonly DTO и Value Objects: `Message`, `ToolCall`, `TokenUsage`, `TaskAssignment`.
* Модели предметной области: `Project`, `Agent`, `Team`, `Session`.
* Репозитории с интерфейсами: `ProjectRepositoryInterface`, `AgentRepositoryInterface`, `SessionRepositoryInterface`.


* [ ] **3.3. Сервис управления контекстом (Context Manager)**
* Сборка системного промпта агента с инжекцией контекста проекта и списка доступных инструментов.
* Форматирование истории сообщений под лимит контекстного окна модели.
* Логика суммаризации (сжатия) устаревших сообщений при приближении к лимиту токенов.

## Этап 4: Подсистема скилов и безопасность

**Цель:** Реализовать модульный реестр инструментов с валидацией прав саб-агентов и строгими схемами параметров.

* [ ] **4.1. Контракты плагинов скилов**
* Интерфейс `SkillInterface` (`getName()`, `getDescription()`, `getParametersSchema()`, `execute()`).
* Объект результата `SkillResult` с разделением флагов успеха, текста вывода, текста ошибок и артефактов.


* [ ] **4.2. Реестр и матрица доступов (Security Layer)**
* `SkillRegistry`: регистрация доступных классов скилов, конвертация их в формат JSON Schema для LLM.
* `PermissionPolicy`: валидатор прав, запрещающий саб-агенту запуск инструментов вне его профиля.


* [ ] **4.3. Базовый набор инструментов:**
* `ReadFileSkill` / `WriteFileSkill` / `ListDirectorySkill`: файловые операции с проверкой `safe_path` (запрет выхода за пределы `/workspace`).
* `DockerExecSkill`: запуск тестов, линтеров и сборок в контейнерах проекта через вызов Go Engine.
* `HostExecSkill`: вспомогательные команды внутри рабочего контейнера.
* `AskHumanExpertSkill`: перевод ноды в режим ожидания ответа оператора с заморозкой контекста.
* `CallSubAgentSkill`: динамическое делегирование подзадачи дочернему агенту.

## Этап 5: Мультиагентный оркестратор и динамическое дерево вызовов

**Цель:** Реализовать цикл автономного принятия решений (ReAct Loop) с поддержкой динамического вызова саб-агентов и изоляцией контекста.

* [ ] **5.1. Автономный цикл одного агента (ReAct Runtime)**
* Цикл: *Task -> Prompt Assembly -> LLM Stream -> Tool Calls -> Execution -> Observations -> Final Answer*.
* Обработка ошибок выполнения инструментов (самокоррекция агента при получении ошибки от линтера/тестов).
* Предохранители: лимит итераций на задачу (`MAX_STEPS`) и контроль таймаутов.


* [ ] **5.2. Динамическое ветвление саб-агентов (Sub-Agent Spawning)**
* Обработка вызова `CallSubAgentSkill`:
* Регистрация дочернего узла (`child_node_id`) в БД со связкой на родителя (`parent_node_id`).
* Создание изолированного контекстного фрейма для саб-агента (только системный промпт роли + срез данных задачи).
* Запуск изолированного цикла выполнения саб-агента.
* Возврат родителю компактного результата (сжатого артефакта) без загрязнения родительской истории промежуточными логами саб-агента.


* Защита от циклической рекурсии: ограничение максимальной глубины дерева вызовов (`MAX_DEPTH`).


* [ ] **5.3. Механизм Human-as-an-Expert**
* Приостановка выполнения агента при вызове `AskHumanExpertSkill`.
* Ожидание ответа пользователя из внешнего события WebSocket.
* Возобновление цикла агента с передачей ответа человека как результата тула.

## Этап 6: WebSocket Hub и шина событий в реальном времени

**Цель:** Обеспечить передачу жизненного цикла графа, стриминга текста и телеметрии в веб-интерфейс без задержек.

* [ ] **6.1. Событийная модель графа**
* Реализация типизированных событий:
* `graph.node_created` (создание новой ноды саб-агента, установка родительской связи).
* `graph.node_stream` (потоковый вывод рассуждений и токенов).
* `graph.tool_call_started` / `graph.tool_call_finished` (статусы вызова инструментов).
* `graph.human_required` / `graph.human_answered` (запрос и получение ответа оператора).
* `graph.node_completed` / `graph.node_failed` (финализация узла с итоговыми метриками токенов и времени).




* [ ] **6.2. Сервер WebSocket (Go Engine)**
* Управление пулом клиентских подключений браузера с привязкой к конкретным сессиям.
* Маршрутизация ответов человека от UI обратно в ядро выполнения.

## Этап 7: Фронтенд — Svelte 5 Web UI и Svelte Flow

**Цель:** Создать веб-интерфейс для настройки проектов, интерактивного наблюдения за графом и диалогами агентов.

* [ ] **7.1. Модуль конфигурации (Settings & Team Builder)**
* Форма настройки целевого проекта (название, путь `/workspace`, стек, имя контейнера, файл гайдлайнов).
* Конструктор саб-агентов:
* Задание роли, системного промпта, модели LLM и температуры.
* Назначение доступных скилов через чекбоксы (матрица прав).
* Назначение Lead-агента команды.


* Настройки эндпоинтов LLM API (Base URL, API Key, параметры модели по умолчанию).


* [ ] **7.2. Интерактивный граф вызовов (@xyflow/svelte)**
* Построение узлов саб-агентов по мере получения событий `graph.node_created`.
* Отрисовка динамических связей (Edges) между вызывающим и вызываемым агентом.
* Кастомный компонент ноды:
* Имя агента и роль.
* Цветовой статус: ожидает, активен, выполняет скил, ждет ответа человека, завершен, ошибка.
* Виджет активного инструмента (например, `docker_exec: vendor/bin/phpunit`).
* Живые счетчики: затраченное время (таймер) и суммарные токены (prompt + completion).




* [ ] **7.3. Инспектор узла и консоль (Sidebar)**
* Открытие детальной информации по клику на узел графа.
* Вкладка **"Диалог"**: полный изолированный контекст саб-агента со стримингом рассуждений в реальном времени.
* Вкладка **"Инструменты"**: лог всех вызовов с возможностью развернуть входные параметры и ответ stdout/stderr.
* Вкладка **"Запрос эксперту"**: карточка с вопросом саб-агента и полем ввода ответа оператора.


* [ ] **7.4. Общая аналитическая панель сессии**
* Сводка метрик всей сессии: суммарное время выполнения задачи, общий расход токенов по моделям, количество итераций саб-агентов.

## Этап 8: Сквозное тестирование и верификация сценариев

**Цель:** Провести end-to-end проверку стабильности системы на реальных сценариях разработки.

* [ ] **8.1. Тест автономной цепочки разработки**
* *Сценарий:* Пользователь ставит задачу: *"Создать класс калькулятора скидок и покрыть его юнит-тестами"*.
* *Проверка:*
1. Главный агент анализирует проект и декомпозирует задачу.
2. Вызов саб-агента `Coder` -> создание файлов в смонтированном томе `/workspace`.
3. Вызов саб-агента `Tester` -> запуск `phpunit`/`jest` в контейнере проекта через `docker.sock`.
4. При падении тестов — передача ошибки `Coder` для исправления кода.
5. Вызов саб-агента `Reviewer` для финальной приемки.




* [ ] **8.2. Тест взаимодействия с человеком**
* *Сценарий:* Агент запрашивает подтверждение бизнес-логики через `AskHumanExpertSkill`.
* *Проверка:* Остановка ноды в графе, появление вопроса в UI, корректное возобновление работы после отправки ответа пользователем.


* [ ] **8.3. Стресс-тест контекстной изоляции**
* Проверка глубоких деревьев вызовов саб-агентов на сохранение компактного контекста и отсутствие переполнения окна токенов.

       │                      │
